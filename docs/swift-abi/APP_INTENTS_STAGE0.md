# App Intents Metadata Feasibility — Stage 0

## Scope and result

**Stage 1 result: no-go on the audited toolchain.** A normal Xcode app build from a Swift `AppIntent` declaration produced `Metadata.appintents`, but the documented public interface is a Swift protocol and its `perform()` requirement is `async throws`. No public, documented interface was found for a Rust/C-defined `AppIntent`, for supplying equivalent compiler metadata to Xcode, or for invoking the metadata processor with a stable input format. The observed processor executable and its command line are Xcode implementation details, not an API contract. This is a scoped Xcode 26.6 result, not a claim about future Xcode releases.

The probe used a temporary iOS app project, Swift source, and build products under `/private/tmp/jc-c7-appintents-stage0.o7vkLp`; none were added to the repository or shipped. The source declared one parameterless `AppIntent` whose `perform()` returned `.result()`. The project was built through `xcodebuild` for a generic iOS Simulator destination with code signing disabled. The build succeeded for `arm64` and `x86_64` simulator slices.

## Public contract and observed implementation details

Apple documents `AppIntent` as a protocol that a type implements to make an app action available to system features. Its public `perform()` requirement is `async throws`; the framework returns an `IntentResult`. Apple’s App Intents configuration documentation says the compiler places app-intent metadata in each bundle at compile time. It describes `AppIntentsPackage` as a Swift protocol: a framework package type marks where framework intent code resides, and an app or extension package may include that package through `includedPackages`.

The one-target probe defined an app intent in the app itself and did not define an `AppIntentsPackage` conformance. It observed the app bundle’s `Metadata.appintents` output, but no separate `AppIntentsPackage` file or output. The documented package relationship is expressed by Swift package types and their `includedPackages` property; the documentation does not define `AppIntentsPackage` as an on-disk metadata format or a Rust/C entry point. For intents in a shared framework, Apple’s documented model places metadata in the framework bundle and uses an app-side `AppIntentsPackage` declaration to include the framework package. That public Swift type relationship is distinct from the Xcode processor’s private build inputs. The framework/app package arrangement was not built in this probe.

| Surface | Audit finding |
|---|---|
| Public App Intents API | `AppIntent`, `perform() async throws`, `IntentResult`, and `AppIntentsPackage` are documented Swift interfaces |
| Public build invocation | `xcodebuild` built an iOS application target from a `.xcodeproj` and scheme |
| Observed Xcode internals | `ExtractAppIntentsMetadata`, `appintentsmetadataprocessor`, `appintentsnltrainingprocessor`, generated file lists, processor options, and `Metadata.appintents` output path |
| Stable Rust/C metadata input | None documented or identified |
| Private runtime registration or metadata generation | Not attempted |

The Xcode build-settings reference documents `INTENTS_CODEGEN_LANGUAGE` for generated Intent classes; it does not document a Rust/C metadata generator or a public contract for the processor invocation seen here. Tool presence, file names, or exported symbols are not treated as support evidence.

## Stage 1 decision and C6 async boundary

A parameterless Rust-defined AppIntent cannot be attempted through a supported public compiler/build mechanism on this toolchain without Swift source. The missing documented contracts are:

- a C/Rust-facing protocol-conformance or type-registration interface for `AppIntent`, including the Swift type metadata and witness behavior expected by the system;
- a stable documented metadata input/schema and public supported tool API that accepts such a Rust/C declaration and emits the app bundle metadata;
- a callable, supported entry path for the system to invoke the Rust-defined `perform()` implementation with the required async result and error semantics.

C6’s final audit is [ASYNC_RUNTIME_ENTRY_FEASIBILITY.md](ASYNC_RUNTIME_ENTRY_FEASIBILITY.md). It found public `Task` and continuation APIs only at the Swift-language layer, no supported C/C++ task-entry/context/resume contract in the inspected headers, module maps, interfaces, or documentation, and no callable async or `Task`-returning wrapper in the generated C++ header for its probe. C6 also notes exported `swift_task_*` names but explicitly does not treat their presence as a public contract. Because App Intents’ `perform()` is async, those findings leave no supported direct Rust task-entry path. `framework-async::OperationState<T,E>` completion/waker state does not create or resume a Swift task and does not fill this gap.

Stage 1 is therefore **unsupported for the audited Xcode 26.6 / SDK 26.5 toolchain**. No private processor invocation, metadata parsing/generation, Swift runtime registration, fabricated protocol witness, or workaround was attempted. Re-audit is needed on an Xcode `27.x` host before making a baseline claim.
