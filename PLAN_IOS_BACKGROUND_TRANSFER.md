## Objective

Add an iOS backend for OS-managed background HTTP(S) downloads via Foundation `URLSessionConfiguration.backgroundSessionConfigurationWithIdentifier`. Keep the response body file-backed, expose durable task state through D10, and reattach to the same session after app relaunch.

The app owns its `UIApplicationDelegate`. On `application(_:handleEventsForBackgroundURLSession:completionHandler:)`, it first retains UIKit's completion handler in app-owned state, creates/reattaches the backend with the supplied identifier, then forwards the retained handler. URLSession may send finish-events before the backend receives that handler; the backend preserves this early event. B13 does not import UIKit or create an app delegate.

## Portable contract (D10; do not edit)

- `TransferId` wraps a private, nonzero `NonZeroU128`; callers retain the same value across app launches.
- `DownloadRequest` is GET-only and owns no body; it carries `HttpUrl`, borrowed `Header` values, and an `AppPath` destination.
- `TransferStatus::Succeeded` owns `StatusCode` and `Vec<ResponseHeader>`. Any HTTP status, including non-2xx, is a completed HTTP response. File or transport errors are `Failed`.
- `start_download` persists acceptance before it returns. An ID with a retained record is a duplicate. `forget` removes only a terminal record and leaves the destination file.
- `cancel` durably records a stop request for queued or active work. Success means the request was recorded; status may remain queued or active until a terminal callback. A terminal result may win the race, and a terminal task is a no-op success.
- A backend reports success only after one atomic destination commit. Atomic visibility does not imply crash durability.

## Backend API and session lifecycle

- `IosTransferBackend::new(session_identifier, MainThreadMarker)` opens the journal and creates a background session with that stable identifier. The identifier is app-unique, dedicated to this backend, and restricted to one safe path segment.
- The backend is `!Send`/`!Sync`, created and dropped on the main thread, and intended to remain app-owned while tasks or forwarded events remain in flight. It does not call `finishTasksAndInvalidate` or `invalidateAndCancel` on drop; URLSession must retain background work for later reattachment.
- The session uses the generated delegate protocol API with a nil delegate queue. Foundation supplies its serial delegate queue. `taskDescription` (`jcd-ios-transfer-v2:<32 lowercase hex TransferId>:<32 lowercase hex incarnation>`) mirrors an app-owned random `NSUUID` incarnation token persisted in the journal. A token, not `taskIdentifier`, proves task identity across relaunch and before initial task reconciliation. `NSURLSessionTask.taskIdentifier` is unique within a live session and is held only in an in-memory `TransferId -> taskIdentifier` map for task-list and cancellation correlation; B13 does not assume it is stable across relaunch.
- On each app launch, route exactly one launch path after UIKit event routing: call `handle_background_events` (or its C-owned callback/context form) when UIKit supplies a background event; otherwise call `finish_launch_without_background_events`. Initial `getAllTasksWithCompletionHandler` reconciliation reattaches only a unique task whose tag token matches its journal token, resumes a suspended task, resubmits a durable queued task that has no matching native task, and marks an absent active task without a commit intent failed on ordinary launch. A recovered commit intent stays active because its destination outcome is unknown. During background-event startup, missing-task finalization waits for `URLSessionDidFinishEventsForBackgroundURLSession`. `start_download` returns `Unavailable` without accepting a new ID while this initial snapshot is pending, preventing stale-snapshot races. Reconciliation cancels all tasks in an ambiguous duplicate-tag group, clears their tags, and leaves the record unattached; unknown/orphan tasks are also cancelled in the dedicated session. `JCDITF01` records and `v1` task tags have no incarnation token: queued records are resubmitted with a new token, while active legacy tasks are cancelled and resolve as `Failed(Unavailable)` (or `Cancelled` for a durable cancel request) unless a commit intent requires staying `Active`.
- `didFinishDownloadingToURL` and `didCompleteWithError` verify the callback's persisted app-owned incarnation token before they adopt data, persist a deferred failure, mutate a record, or remove the live task-map entry. This permits a valid callback before task-list reconciliation without accepting an old callback for a reused `TransferId`; if a live task-map entry exists, its `taskIdentifier` must also match. Each task receives a fresh NSUUID token; the backend creates one native task per token, persists the token before resume, and replaces the token before queued resubmission. Thus duplicate tasks for one TransferId have distinct tokens under backend control, and only the journal-matching token may act before reconciliation cancels the duplicate group. Same-token duplication from UUID collision or external task mutation is outside the guarantee; reconciliation cancels the group. A matching early `didFinishDownloadingToURL` may adopt before duplicate detection; if reconciliation clears that task tag before `didCompleteWithError`, the callback cannot be correlated. Missing-task finalization may persist `Succeeded` before that callback only when this live process has proof that B14 returned `Atomic`; without that proof, the durable intent remains `Active`. Deferred validation/adoption failures are memory-only and keyed by `(TransferId, incarnation)` until that final callback; queued replacement with a fresh token discards prior-incarnation failures so the new task cannot inherit them. This prevents an old task from terminalizing a record and then mutating a later reused `TransferId`. Cancellation captures the expected incarnation and optional live task identifier, then rechecks both before cancelling. If the process exits before the final callback, an absent non-intent active record resolves as `Failed(Unavailable)`; the in-memory deferred failure is lost. A stale callback with a different incarnation after ID reuse is ignored.
- The app forwards the exact session identifier and completion block. The backend copies and retains one handler, rejects a second concurrent handler, and consumes it once after both the initial task reconciliation and URLSession finish-events callback. URLSession may deliver its finish-events callback on a secondary queue; the system handler runs on the main dispatch queue. The C-owned seam calls an `unsafe extern "C" fn(*mut c_void)` on main; its context must remain valid through that call and must not unwind. The C client must retain the backend/context until then.
- `MainThreadBound` drop normally sync-dispatches to main and may deadlock if the main runloop is not running. The event path avoids background drop: it moves the bound block into a `Send` main-queue closure, extracts it there, invokes once, then drops it on main. The backend is `!Send`, must be dropped on main, and its `Drop` releases a pending block on main without invoking it. Keep the backend alive through the callback; do not rely on drop to complete a UIKit event.

## Durable journal and state transitions

- Records live under `ApplicationSupport/ios-transfer/<session-identifier>/<transfer-id>.record`; each transfer ID is 32 lowercase hex digits. New private binary records start with `JCDITF02`, have a 1 MiB bound, and store the ID, optional app-owned task-incarnation token, URL, request headers, semantic destination, cancel-request bit, status, optional pre-commit intent with HTTP metadata, or terminal metadata/error codes. The decoder accepts prior `JCDITF01` records without a token and applies the conservative legacy-task handling above.
- `ios-files` creates or replaces each record with `RequireAtomic`; B14 adoption creates a private stage in the destination directory and commits via atomic `renameat`. Neither operation promises `fsync` or power-loss durability. Journal records are sandbox data and are not encrypted by this crate.
- Start validates Foundation URL/header conversion, assigns a new nonzero `NSUUID` incarnation, creates a suspended GET download task with the matching v2 task description, writes `Queued` plus the token, registers the live `taskIdentifier`, resumes the task, then attempts an `Active` status write. If that optional write fails, accepted work remains durably `Queued`, the method still returns success, and a later reconciliation or terminal callback updates it. If the required queued-record write fails, it cancels the still-suspended task and returns the write error without accepting the ID.
- A matching task's final `didCompleteWithError` callback persists its terminal result. Missing-task finalization also resolves an absent active record: without an intent it persists `Failed(Unavailable)` or `Cancelled`, and with a live `Atomic` adoption proof it may persist `Succeeded`. A recovered intent without live proof stays `Active`. A validation/adoption failure first observed in `didFinishDownloadingToURL` is held in memory until the matching final callback; if the process exits first, ordinary/background reconciliation resolves an absent non-intent `Active` record to `Failed(Unavailable)`. The initial task snapshot plus the app's launch path resolves a missing `Active` record: ordinary launch marks it failed; background-event launch waits for finish-events. A durable cancel bit prevents a queued task from being resubmitted.
- On successful download, convert status and response headers and size-preflight both the terminal record and a commit-intent record before touching the destination. Persist the active commit intent, including owned HTTP metadata, then call B14 synchronously before the delegate returns. A matching later task-completion callback or same-process missing-task finalization may write terminal `Succeeded` only if this live process knows B14 returned `Atomic`; a recovered intent begins without such in-memory proof, so task completion or cancellation alone leaves it nonterminal. A new matching download callback can re-adopt the file; only a fresh B14 `Atomic` return establishes proof for later terminal success. Replay parse, destination-validation, or adoption errors also preserve the intent as `Active` unless this process has positive adoption proof. A first-attempt B14 adoption error proves the destination rename did not occur. B13 tries to clear the intent durably and defers `Failed` until the matching final task callback. If that intent-clear write fails, B13 still clears the intent in live state and retains an incarnation-keyed deferred failure so the final callback can persist `Failed`; the disk journal may still hold the old `Active` intent. If the process exits before terminal persistence, recovery keeps that durable intent `Active` rather than infer an outcome from memory that was lost. If terminal persistence fails, the terminal result is retained in memory and retried on later `status` or `forget`; terminal `cancel` is no-op success before retry, and the last successfully persisted journal record remains authoritative on disk. After successful adoption, that record is the active commit intent. After a first-attempt B14 adoption error with successful intent clearing, it is `Active` without an intent, so missing-task reconciliation can resolve it as `Failed(Unavailable)` or `Cancelled` according to the durable cancel bit. If intent clearing failed, the disk still has the active intent and recovery keeps it `Active`. An unresolved durable intent can remain `Active` indefinitely because B14 exposes no transaction receipt or rollback to determine whether rename occurred; D10 guarantees the last durable status after relaunch, not eventual terminality. `cancel` while this intent is present still records the request but cannot terminalize the ID; `forget` returns `NotTerminal`. Response metadata over the 1 MiB record bound fails with `ResourceExhausted` before destination adoption.

## Native behavior and parity limits

- The request is GET-only. Request header values must be UTF-8 for `NSString`; non-UTF-8 values return `Unsupported` before task acceptance. `NSMutableURLRequest.addValue_forHTTPHeaderField` combines duplicate fields; Foundation/URLSession may normalize spelling, order, and defaults. Exact wire-level request-header fidelity is not promised.
- `NSHTTPURLResponse.allHeaderFields` returns `NSDictionary`; duplicate response headers and source order cannot be preserved. B13 sorts observed names for stable journal output. String values are copied as UTF-8; `NSNumber` values use `stringValue`. Invalid or unsupported metadata fails before destination adoption.
- All HTTP statuses remain ordinary download results. B13 does not set request cache policy, cookie policy, redirect policy, timeout, connectivity policy, or authentication challenge policy; Foundation owns those defaults.
- Background transfer survives ordinary suspension and can trigger app relaunch when the OS permits. A user force-quit cancels transfers and suppresses automatic relaunch. No continuation guarantee applies after force-quit, OS resource policy, or power loss.
- The effective iOS API floor is iOS 10.0, inherited from the existing `ios-files` surface. Background URLSession itself is documented from iOS 7.0; it does not lower B14's floor. B14 records Xcode 26.6 / iOS 26.5 SDK evidence for its own API floor.
- No progress stream, upload, request body, custom retry, redirect override, generic connection pool, or process-global task registry.
